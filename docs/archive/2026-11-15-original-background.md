Key points:

1. **Coding agents can already perform tasks on real robots, but "thinking too long" can make them clumsy.** They asked Claude Code to open a door and enter a room: without a dedicated door detector or planner, it used only the camera and robot feedback to find the handle, open the door, and drive through. However, the agent sometimes thought for more than **a minute** before moving, then collided with the environment or mishandled a precise placement. The team wanted to understand how coding agents actually work behind the scenes on robotics tasks.
2. **Three real-world tasks, comparing two agents or models.** The captions render the names as "Kuka with 5.5 and Kortex with 56 Astra," apparently referring to two coding agents or models; their names cannot be reliably reconstructed from the captions. The three tasks were **(1) putting fruit in a basket** (a simple tabletop task); **(2) a precision tabletop task**: placing a ball on a rack and taking it back (later captions say "bolt rack," so the object description is inconsistent); and **(3) mobile manipulation**: going through a door. The agents controlled the robots using only very basic tools, with all motion routed through the team's control service. They divided agent operation into two stages: a **learning stage**, in which the agent encountered the task for the first time, solved it, and wrote down skills; then a second stage in a new session, with no access to the previous conversation but permission to read the skill written in the first stage. Overall, both systems completed all fruit and door-opening trials; **neither succeeded at the rack task, which required more precise contact**. Learning a task took a few minutes, which was acceptable because it happened only once. The real issue was the **execution** cost paid every time. A rough estimate for clearing a table with objects on it approached **an hour**; by their accounting, it could even take several hours and cost nearly **$100**, which the speaker considered unacceptable.
3. **Where the time goes: very little into robot motion, and most into model reasoning.** The agent works in a loop: inspect camera images, think about the next step, and act; if the goal has not been reached, inspect or verify and think again; once it has been reached, think about the next step. Robot motion accounts for only a small fraction of the total time. Most of the rest is model inference between actions. Most reasoning is spent deciding the next action, with the remainder spent rechecking results, running geometry code, and deciding to wait. Model reasoning sets the pace, rather than robot motion. In one example, the hand was already above the basket, but the agent kept estimating dimensions, looking for the basket rim, and checking images. Only after **more than two minutes** did it make a small correction of a few centimeters. Waiting also wastes time: the agent calls sleep while robot motions execute and often keeps waiting after the motion has already finished. During learning, the agent writes its own tools, such as geometry utilities, planners, and skill files, but the model still makes the critical decisions: how and where to make contact, and how to respond to feedback. For example, while loading the basket, it decided to locate the basket again from a new image. Reusing an existing skill saves time, but the model still needs substantial "refreshing"; the captions say **Astra saved only 10% of the time**.
4. **Safety judgments arrive too late, and unit errors are amplified.** These judgments are especially important for safety. In one case, the agent had already noticed force on the arm and intended to retract, but the model was deep in thought and did not retract until about **a minute later**. The team also observed unnoticed contact with the table and collisions that forced the operator to use the emergency stop. In these cases, the model still considered the motion complete: task success and robot safety were not aligned. In an extreme example, the agent sent an angle in **degrees**, while the tool expected **radians**. On the real robot, this unit error made the rotation nearly **60 times** the intended amount.
5. **Giving the robot more tools did not help as much as expected.** The original tools only supported moving, looking, and grasping. The team added perception-based segmentation, reachable-pose search, waypoint collection, collision detection, and whole-body motion planning. Unexpectedly, the additional tools helped less than anticipated: **the success rate even declined**, and successful runs were slower and more expensive than before. The team checked that the model was using these tools on almost every run. Time was merely shifted elsewhere: more tools meant more time spent querying and checking. Adding tools did not eliminate work; it moved the work. **Tools help only when their outputs can feed directly into the next decision.** The speaker viewed this as an engineering problem: how to package tools into skills that the agent can trust and rely on.
6. **Rehearsing in simulation: agents refused it for easy tasks and built simulations for hard ones, but success remained low.** Agents were allowed to build simulations for all three tasks. For the fruit and door tasks, they **refused**, considering the tasks too simple and saying, in effect, "I can handle this myself"—the speaker described them as very confident. For the precision rack task, they recognized the difficulty and the need for simulation. They built scenes from depth data and images, but often guessed contact parameters such as mass and friction from prior knowledge. The speaker observed that agents cared more about matching the physics than achieving photorealism and were reluctant to spend many tokens on textures. Once the simulation was ready, they rehearsed and gradually improved strategies such as grasping the ball. After extensive trials, they switched to the correct strategy and then tried it on the real robot; the same strategy could lift the ball and place it on the rack in the real world. However, this often required **well over half an hour** in simulation versus only a few minutes on the real robot, and **only 23% of the experiments actually succeeded**.
7. **Three problems remain: time, safety, and motor skills; compared with coding environments, a large language model alone is not enough.** A single model call takes seconds, and the full image–reasoning–reaction loop takes longer. The robot receives a new command only every **few seconds**, while policies running real robots update many times per second. Models capable of this reasoning are an order of magnitude too slow. When writing code, people can wait or get coffee; the physical world keeps moving and cannot wait. For safety, a coding agent can revert changes without "ruining lives"; robots have no undo. The speaker returned to the pushing example: the agent already knew the force was high, yet continued pushing. In a safety-critical situation, stopping must happen **right now, within the current second**, without waiting for the model. As for motor skills, coding agents have precise building blocks such as reading logs and writing files. Robot skills involve continuous contact processes, many of which are not yet mature enough for direct use in the real world.
8. **Their goal is an "AI-native" robotics system: a reliable, layered stack built around slow models.** In the cloud, an LLM-centered agent system uses a harness with memory, context, task tracking, and other capabilities to turn user requests into plans and subtasks, operating below **0.5 Hz** (the captions say "0.5 h"; Hz is inferred from the context and the same layered terminology used by Wentao). On the device, task execution turns each subtask into motor-skill commands at roughly **1–2 Hz**, such as motion planning and navigation planning, with subtask monitoring to decide whether the task is complete or a different skill is needed. Below that is a primitive-skill layer, such as motion tracking, at roughly **20–100 Hz**. At the bottom are robot services that protect hardware through collision avoidance and local motion planning. The captions render the rate as "212 1000 h," probably on the order of **200–1000 Hz**, though the numbers are imprecise. The team has already studied parts of this stack. One recent effort concerns **memory systems for embodied agents**: a benchmark comparing different representations. The setup is realistic—the robot observes events **before** it knows the question, such as observing a scene and later being asked "Where is my phone?", or moving a lemon and later being asked about the apple beside it. They found that **storing camera frames provides clearer information and higher success rates than storing textual descriptions**, because frames preserve more information. Scene graphs can help a large language model understand images, but scene graphs alone help less than images do. More surprisingly, **storing images actually costs less**: inputs become larger and input costs rise, but the richer information greatly reduces model reasoning steps, lowering the cost per successful request. Saving a frame is also cheaper than writing a description. The second area is **task-completion detection**. In RoboLab experiments, they ran what the captions call "Pi Zero on fire" (possibly a policy such as π0; the latter part cannot be reconstructed). If left running without being stopped, the policy continued moving after the task was complete, with no sense of "I'm done." They tested existing models' ability to judge completion: the best models could usually do so, but checking at high frequency was very expensive; fast models performed close to random guessing. Even when given facts or ground truth from simulation, fast models remained near random guessing with almost no improvement, while the better models were nearly perfect. Their conclusion was that real-world operation requires **training their own VLM for task tracking**. The closing message was that large language models can already handle a substantial part of robotics semantics—understanding requests and planning—but this brings us back to many classic robotics problems: how to build reliable systems around slow models, handle scenes correctly, design clear interfaces between modules, and obtain motor skills that are fast, safe, and dependable. The speaker said it felt a little like going back to 2019 and returning to robotics' longstanding problems.

Q&A: Someone asked whether this layered agent architecture could scale to dexterous manipulation, and at which interface layer the agent should operate. Tianyu said dexterous manipulation is among the hardest robotics tasks, involving extensive contact and **high-frequency responses** to the state of objects and hands. He did not believe a large language model alone could solve it end to end; a layered approach is essential. The lowest layer is hardware self-protection, such as preventing joints from exceeding limits. Above that is compliant control, which responds to object shapes and environmental disturbances. The LLM-based agent does more of the semantic work: giving the lower-level compliant controller a stream of commands specifying goals, translating the user's semantic messages into a more continuous action space for the low-level controller to execute.
